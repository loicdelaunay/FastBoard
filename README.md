# FastBoard

Outil de suivi de projet collaboratif en **temps réel**, entre Trello et Jira : tableau Kanban, liste, diagramme de Gantt et analyseur, avec comptes, rôles et permissions.

**Stack** : Vue 3 + TypeScript + [PrimeVue 4](https://primevue.dev) · Node 24 (Express 5, WebSocket `ws`) · SQLite (`node:sqlite`, aucune dépendance native).

## Démarrage rapide

Prérequis : **Node ≥ 24** (SQLite intégré et exécution native de TypeScript).

```bash
npm install
npm run dev          # API sur :3000 + interface Vite sur http://localhost:5173
```

Production (un seul processus, interface servie par le serveur) :

```bash
npm run build
npm run start:prod   # http://localhost:3000
```

Pour mettre à jour : récupérez la nouvelle version, relancez `npm install` et `npm run build`, puis redémarrez le serveur. Les deux étapes comptent : si l'interface n'est pas reconstruite (ou le serveur pas redémarré), les navigateurs affichent « Mise à jour incomplète sur le serveur » (ou « Le serveur n'a pas redémarré ») avec les deux numéros de version, et le serveur le signale dans son journal au démarrage.

### Application installable (PWA)

FastBoard s'installe comme une application, sur ordinateur comme sur téléphone : menu du compte → « Installer l'application » (Chrome, Edge, Android), ou, avec Safari, les consignes affichées (iPhone et iPad : Partager → « Sur l'écran d'accueil » ; Mac : Fichier → « Ajouter au Dock »). Elle s'ouvre dans sa propre fenêtre, aux couleurs du thème, avec le nom et le logo de *Administration → Personnalisation* (ses icônes sont tirées du logo), des raccourcis vers les modules activés et le nombre de notifications non lues sur son icône. Son service worker (construit avec l'interface) garde l'interface et les écrans déjà ouverts : elle s'ouvre même sans réseau, et les pages passent toujours d'abord par le réseau (pas d'interface périmée après une mise à jour). **L’installation demande HTTPS** avec un certificat reconnu par les appareils (ou `localhost`) : voir *Administration → HTTP / HTTPS* ; un certificat auto-signé ne suffit pas, les navigateurs n’y acceptent pas de service worker.

### Lecture seule hors ligne

Si le serveur ne répond plus (arrêt, redémarrage, réseau coupé), FastBoard continue **en lecture seule** avec ce qu'il a gardé sur l'appareil : les réponses de l'API déjà reçues (projets, tickets, espaces, arbres, notifications…), le texte des notes et les éléments des tableaux déjà ouverts, et leurs images. Un bandeau le signale et donne l'âge des données affichées ; toute modification est refusée (rien ne serait enregistré), les éditeurs passent en lecture, et une note ou un tableau jamais ouvert sur l'appareil le dit. Le serveur est sondé toutes les 5 secondes : dès qu'il répond, le bandeau l'annonce, les écrans se rechargent et l'écriture revient. Ces données sont rangées dans le navigateur (IndexedDB), par compte, sans l'administration, l'assistant IA, les jetons, les exports ni les recherches, et s'effacent à la déconnexion. En HTTP, un onglet déjà ouvert continue ainsi ; pour **rouvrir** l'application sans serveur (nouvel onglet, application installée), il faut HTTPS ou `localhost`, où le service worker garde aussi l'interface et les images.

**Garder un espace hors ligne** : clic droit sur un espace de documentation, un espace de tableaux blancs ou un projet → « Garder hors ligne ». Tout son contenu est copié sur l'appareil, y compris ce qui n'a jamais été ouvert : arbre, notes et modèles avec leurs commentaires, tableaux blancs (éléments, aperçus, images et icônes ajoutées), tickets avec leurs commentaires, leur historique et leurs pièces jointes (images en aperçu, et tous les fichiers jusqu'à 50 Mo chacun). La copie se refait toutes les heures tant que l'application est ouverte (et au retour du serveur après une coupure) ; une pastille sur la carte donne l'heure de la dernière copie, l'avancement ou un échec, et le même menu propose « Actualiser la copie hors ligne » et « Ne plus garder hors ligne ». Ces copies échappent au ménage du cache et le navigateur est prié de ne pas les effacer de lui-même ; elles appartiennent au compte et partent à la déconnexion (ou à la connexion d'un autre compte). Les fichiers joints se rouvrent sans serveur là où le service worker fonctionne (HTTPS ou `localhost`).

### Exécutable autonome (Windows)

Un seul fichier `FastBoard.exe` embarque Node, le serveur et l'interface : aucune installation requise.

```bash
npm run build:exe        # construit release/FastBoard.exe (≈ 90 Mo)
```

Pour qu'il démarre tout seul avec la machine et se relance en cas d'arrêt : *Administration → Installation* (tâche planifiée Windows, unité systemd sous Linux, agent launchd sous macOS ; commandes manuelles affichées si les droits manquent). Double-cliquez sur l'exécutable (ou lancez-le dans un terminal) : le serveur démarre sur http://localhost:3000 et ouvre le navigateur. La base `data/fastboard.sqlite` et les pièces jointes `data/uploads/` sont créées **à côté de l'exécutable** ; les variables d'environnement ci-dessous (`PORT`, `FASTBOARD_DB`…) fonctionnent aussi, et `FASTBOARD_NO_OPEN=1` empêche l'ouverture du navigateur. L'exécutable se construit avec la version de Node qui exécute `npm run build:exe` (≥ 24) ; il n'est pas signé, Windows SmartScreen peut donc demander une confirmation au premier lancement.

Au premier lancement, le serveur crée la base `data/fastboard.sqlite` et le compte **super administrateur** :

| E-mail | Mot de passe |
| --- | --- |
| `admin@admin.com` | `admin1234` |

> Changez ce mot de passe dès la première connexion (menu du compte → Sécurité).

Jeu de données de démonstration (facultatif) : `npm run seed:demo` crée 4 utilisateurs (`camille@demo.fr`, `hugo@demo.fr`, `ines@demo.fr`, `theo@demo.fr`, mot de passe `demo1234`) et un projet avec livraisons, tickets et discussions.

## Fonctionnalités

**Collaboration temps réel (WebSocket)** — chaque modification (ticket, commentaire, déplacement, catégorie, livraison, membre…) est diffusée instantanément à tous les membres du projet ouvert. Indicateur de connexion, reconnexion automatique avec resynchronisation, présence des collègues (et de ceux qui consultent un ticket), mise en évidence des tickets modifiés par un autre.

**Cinq onglets** par projet ; les quatre premiers partagent leurs filtres (recherche, catégories, livraisons, personnes, statuts, « mes tickets », « en retard ») :
- **Analyseur** — indicateurs clés, réel vs théorique, burn-down, charge par personne, répartition par statut et catégorie, points de vigilance, priorités de suivi ; par livraison ou global (liste déroulante des versions).
- **Liste** — tableau triable avec regroupement (livraison, catégorie, statut, priorité), **filtres par valeur dans les en-têtes** (catégorie, priorité, composants, statut, assignés, livraison), changement de statut rapide, export CSV.
- **Kanban** — glisser-déposer entre colonnes et réordonnancement, ajout rapide dans une colonne, menu « Déplacer vers » pour le tactile et le clavier. Le menu ⋯ de la colonne « Terminé » choisit les tickets terminés affichés (tous, sans ceux des livraisons passées, aucun), pour soi ; une pastille compte les masqués, et la recherche les trouve toujours.
- **Gantt** — frise avec **numéros de semaine ISO**, zoom jour / semaine / mois, regroupement par livraison ou par personne (avec détection de surcharge), barres déplaçables et redimensionnables à la souris ou au clavier, livraisons en barres récapitulatives, ligne « aujourd'hui ».
- **Activités** — le fil de tout ce qui se passe sur le tableau, en direct : tickets créés, déplacés, modifiés, assignés, parts terminées, commentaires, catégories, livraisons, membres, réglages du projet. Regroupé par jour, avec filtres (type, personne, recherche, origine : interface ou API / agents), pagination, pastille de nouveautés sur l'onglet et mention « via <jeton> » pour les actions faites par une IA.

**Tickets** — titre, description, statut, **catégorie** (réglable par projet), **livraison ciblée** (avec mémorisation de la livraison initiale pour repérer les reports), dates, **lignes d'avancement** : chaque ligne a un texte, une **personne facultative** (plusieurs lignes par personne possibles), un pourcentage et une case « terminé » ; le bouton + en ajoute, on les réordonne en les glissant. L'**avancement global** est la moyenne des lignes et s'affiche partout. Quand toutes les lignes sont terminées, le ticket passe automatiquement à « Terminé » ; une ligne rouverte le relance. **Priorité** et **composants** (listes réglables par projet : nom, icône, couleur), **dépendances** vers d'autres tickets avec une raison (liste ou texte libre ; un ticket bloqué affiche un cadenas). **Mentions `@`** de personnes et de tickets dans la description et les commentaires. **Historique** complet des modifications (avec « via <jeton> » pour les actions d'une IA) et **commentaires** avec réponses imbriquées (modifier / supprimer).

**Export PDF de l'analyseur** — bouton « Exporter en PDF » sur chaque périmètre (ensemble du projet ou une livraison, aussi depuis le tableau des livraisons) : indicateurs, réel vs théorique, graphiques (statuts, burn-down, charge, catégories), points de vigilance, priorités, livraisons et liste des tickets. Généré dans le navigateur (jsPDF, chargé à la demande), dans la langue de l'interface.

**Langues (français / anglais)** — le choix se fait sur la page de connexion ou dans *Mon compte → Apparence*, il est enregistré sur le compte et la page se recharge. Le français est la langue source : ses textes servent de clés (`src/i18n/index.ts`), l'anglais est dans `src/i18n/en.*.ts` et un test vérifie que chaque texte de l'interface est traduit. Dates, noms de mois, unités, messages d'erreur du serveur et libellés PrimeVue suivent la langue ; les journaux serveur et la documentation de l'API restent en français. Pour ajouter une langue : ajouter son code dans `shared/locales.ts` et un catalogue `en.*.ts` équivalent.

**Réglages du projet** — onglet *Colonnes* : renommer, recolorer, réordonner et masquer (si vide) les colonnes du Kanban ; les noms et couleurs suivent partout (liste, Gantt, filtres, analyseur, historique). Les statuts restent fixes car ils portent les règles d'avancement ; « Terminé » ne se masque pas. Onglet *Automatisation* : passage automatique dans « Terminé » quand toutes les parts sont finies (désactivable), réouverture automatique, **confettis** quand un ticket arrive dans Terminé (désactivés si le système réduit les animations) et **indicateur d'inactivité** façon Jira (barre sur les cartes : depuis combien de jours le ticket n'a pas changé de colonne), et masquage des tickets terminés des livraisons passées (date de fin dépassée) dans la colonne « Terminé ». Colonnes dans lesquelles un ticket compte pour 100 % (par exemple « À tester »), tri automatique des cartes par colonne (priorité, échéance, titre…), pastille colorée sur les tickets dont la livraison approche (seuils réglables). Onglets *Priorités* et *Composants*. Réglages modifiables via l'API (`PATCH /projects/{id}` → `settings`).

**Pièces jointes** — dans un ticket, glissez-déposez des fichiers n'importe où (ou collez une capture d'écran, ou utilisez « Ajouter ») : envoi en parallèle avec barre de progression, vignettes et aperçu plein écran des images, téléchargement, suppression et remplacement d'une image au clic droit (par l'auteur ou un modérateur). Elles sont historisées, visibles dans les Activités, comptées sur les cartes, synchronisées en temps réel et disponibles par l'API. Les images envoyées (ici, dans les notes et sur les tableaux blancs) sont converties en WebP, qualité 80 %, pour prendre moins de place ; les GIF, les SVG et les autres fichiers partent tels quels. 25 Mo par fichier et 30 par ticket ; stockées sur disque à côté de la base (`data/uploads/`), servies en téléchargement isolé (jamais de HTML ni de SVG en ligne).

**Livraisons** — nom, date de début, date de fin, couleur, description.

**Menu contextuel des tickets** — clic droit sur un ticket (Kanban, liste, Gantt) ou bouton « ⋯ » d'une carte : ouvrir, copier le lien ou la clé, déplacer vers un statut, s'assigner / se retirer, terminer ou rouvrir sa part, dupliquer, **supprimer** (avec confirmation). Les entrées dépendent des permissions ; la suppression est aussi dans l'en-tête et le détail du ticket.

**Documentation** — à activer dans *Administration → Documentation* : l'onglet « Documentations » apparaît à droite de « Projets ». Chaque espace est un dossier sur le serveur (`data/docs/<id>/`) qui contient de vrais fichiers Markdown, en dossiers et sous-dossiers, et ses images. Les membres ont un rôle (Lecteur, Éditeur, Propriétaire). On lit le rendu, on écrit dans le source avec un aperçu, ou on passe en « Lecture et écriture », où un clic sur un bloc rendu le modifie sur place ; dans tous les cas à plusieurs, en temps réel, curseurs visibles, avec Mermaid, les formules et les liens `[[wiki]]`. Une barre d'outils, les commandes `/` et le clic droit accélèrent l'écriture, et un sommaire à gauche de la note reprend ses titres, en lecture comme en « Lecture et écriture ». Ce mode fonctionne comme Obsidian : le texte reste rendu, et seule la syntaxe sous le curseur réapparaît. Les notes s'ouvrent dans des onglets, avec leurs flèches précédent et suivant (les adresses web, elles, s'ouvrent dans un autre onglet du navigateur) ; rétroliens, liens, commentaires et compte des mots sont en bas à droite. Chaque espace accepte, s'il le veut, la syntaxe d'Obsidian (callouts, surlignage, coloré par une bille emoji comme `==🟢 Validé==`, commentaires, étiquettes, notes de bas de page, propriétés, notes intégrées) et peut devenir un site web en lecture seule (`/wiki/…`), ouvert à ses membres, à des personnes choisies ou à tout le monde, à la manière de Docusaurus : page d'accueil par sections, recherche (Ctrl K), sommaire qui suit la lecture, pages précédente et suivante, thème clair ou sombre. Les tableaux s'écrivent directement dans leurs cellules, le clic droit ouvre un bloc rendu en Markdown brut, et les images s'agrandissent en plein écran. Chaque espace a ses modèles de notes (section *Modèles* en bas de l’arbre) : on en écrit un, ou on enregistre une note comme modèle d’un clic droit ; une nouvelle note part d’un modèle au choix, et « Insérer un modèle » le pose au curseur. Comme dans Obsidian, `{{title}}`, `{{date}}` (avec un format, `{{date:DD/MM/YYYY}}`), `{{time}}` et `{{author}}` y sont remplis. On met des notes en favori, et les dossiers et fichiers portent une note sur leur rôle, qui s’affiche dans une petite fenêtre au survol de leur ligne. Un dossier change d’icône et de couleur d’un clic droit (« Icône et couleur… ») ; le site web de l’espace les reprend. Comme dans Obsidian, les titres se replient à tous les niveaux : la flèche qui apparaît à gauche d’un titre cache sa section jusqu’au titre suivant de même niveau ou plus haut (Ctrl Maj [ et ] dans l’éditeur), en Lecture, en Écriture et en Lecture et écriture ; les titres repliés d’une note sont retenus sur l’appareil, et un lien ou le sommaire qui y mène les déplie. Un passage sélectionné se commente d'un clic droit, avec mentions, réponses et résolution ; un panneau montre les liens et rétroliens de la note. Chaque note garde 15 jours d'historique, et les fichiers supprimés 15 jours de corbeille. Une version se nomme d'une étiquette (« v1.0 », « Validé client »…) : elle n'est alors jamais effacée, ses images sont figées avec elle (même remplacées ou supprimées ensuite ; copier ou restaurer la version les remet dans l'espace), et elle se cite avec `@` (`@[Guide · v1.0](doc:12#v:345)`), le lien ouvrant cette version précise. Le sélecteur de version de la barre de la note passe d'un clic à une version étiquetée ou récente ; une ancienne version s'affiche en lecture seule, avec « Copier pour modifier » (une nouvelle note qui la reprend) et « Dernière version ». Ctrl F cherche dans la note avec la syntaxe de recherche d'Obsidian (`"phrase"`, `OR`, `-mot`, `/regex/`, `match-case:`, `tag:`, `task-todo:`, `line:( )`, `section:( )`…), Markdown compris en écriture ; Ctrl H remplace. Une image collée ou glissée dans une note est rangée dans un sous-dossier à côté d'elle, `Pictures` par défaut : son nom se règle pour tout le site dans *Administration → Documentation*, et chaque espace peut choisir le sien dans ses réglages. `[[` propose les notes et les images de l'espace (avec leur miniature), `[[#` les titres de la note ; les images acceptent la taille d'Obsidian (`![[image.png|300]]`). Le `@` mentionne personnes, tickets et fichiers, et les tickets peuvent mentionner des fichiers. D'un clic droit, un espace ou un dossier s'exporte en ZIP, à l'exacte image de son arborescence (un coffre lisible par Obsidian), et une note s'exporte en `.md`. À l'import d'un ZIP ou d'un `.md`, ce qui existe déjà passe par un comparateur : les deux versions côte à côte, ce qui est ajouté, retiré ou changé, un choix bloc par bloc et un résultat modifiable. Il retrouve aussi ce qui a changé de chaque côté grâce au texte d'origine, gardé 90 jours sur le serveur. Le même comparateur sert dans l'historique, pour ne reprendre qu'une partie d'une ancienne version. La recherche générale trouve aussi les documents. Dans l’arbre des fichiers, on sélectionne plusieurs éléments comme dans un explorateur (Ctrl ou Maj + clic), et « Actualiser depuis le disque » (réglages de l’espace) relit le dossier de l’espace pour y faire entrer les fichiers ajoutés ou modifiés à la main. Un espace où l’on n’entre que par ses droits d’administration porte la pastille « Accès avec droit admin ». Une image se remplace d’un clic droit (« Remplacer l’image… », dans l’arbre ou dans une note) : elle garde son nom, les notes qui la montrent affichent la nouvelle, et l’ancienne reste 15 jours dans la corbeille. Comme dans Figma, un clic sur l’avatar d’une personne présente sur la note la suit : la page défile là où elle lit, et s’ouvre sur les notes où elle va, jusqu’à la première action.

**Tableaux blancs** — entrée « Tableaux blancs » de la barre latérale (activée d'office, à couper dans *Administration → Tableaux blancs*) : des espaces avec membres et rôles, comme la documentation, qui rangent des tableaux en dossiers et sous-dossiers. Un tableau, à la manière de Whimsical, est un plan infini qu'on déplace et zoome, dessiné à plusieurs en temps réel : chacun voit le curseur et le nom des autres, ce qu’ils ont sélectionné et les éléments qu’ils déplacent. Le propriétaire de l’espace peut aussi partager un tableau par une adresse (*Partager*) : à toutes les personnes connectées, à une liste de personnes ou à tout le monde sans compte (le visiteur choisit le nom affiché à côté de son curseur), en lecture ou en modification, avec un mot de passe au choix. La barre latérale du tableau propose cinq modes : *Diagramme* (formes, liens tirés depuis les points bleus d'une forme, sections, tableaux de données et graphiques Chart.js), *Post-it* (en couleurs, avec votes ; leur texte grandit en dézoomant pour rester lisible), *Carte mentale* (Tab ou le « + » du nœud choisi pour un enfant, Entrée pour un frère, mise en page automatique ; un ou plusieurs nœuds se glissent avec leurs branches sur un autre nœud, et Alt + flèches les monte, les descend ou change leur niveau) et *Dessin libre* (crayon, surligneur, gomme). Un *Fast Element* montre un ticket, une note, un dossier, un espace de documentation ou un autre tableau, tenu à jour. Comme dans Whimsical, une sélection se groupe (Ctrl G, clic droit ou barre de sélection) et se dégroupe (Ctrl Maj G) : un clic, ou un cadre de sélection qui en touche un élément, prend tout le groupe, qui se déplace, se copie, s’aligne, se verrouille et se supprime d’un bloc ; un double-clic entre dans le groupe pour n’en prendre qu’un élément (les nœuds de carte mentale, rangés par leur carte, ne se groupent pas). Une sélection s'exporte en Markdown Mermaid (à copier ou en `.md`), et un organigramme ou une carte mentale Mermaid s'importe, mis en page automatiquement. Le `@` mentionne un tableau dans la documentation et les tickets, avec son aperçu au survol. Seul sur sa ligne, il s’affiche en carte ; comme dans Whimsical, on choisit son affichage (lien, carte, image seule, ou vue intégrée où l’on se déplace et où l’on zoome) dans la petite barre qui suit le `@`, au survol du tableau affiché ou au clic droit. Cela s’écrit `@[Titre](board:7#image)`, `#embed` ou `#link`. Le clic droit ou la touche `/` ouvrent un ajout rapide avec recherche : formes, textes, post-it, plus de 2 000 icônes recolorables (bibliothèque Lucide, complétée par les SVG que les administrateurs ajoutent dans *Administration → Tableaux blancs*), images et SVG envoyés dans l’espace (aussi par glisser-déposer ou en collant) et modèles. Un modèle, à la manière d’un « prefab », naît d’une sélection (clic droit, *Créer un modèle*) : ses copies se posent en un clic, signalent quand le modèle a changé et se remettent à jour, et il se modifie dans sa propre vue (section *Modèles* de l’arbre). Le bouton ↪ du tableau liste ses rétroliens. Le clic droit sur une image propose « Remplacer l’image… » (elle garde sa place et sa largeur). L’assistant IA lit les tableaux et, si on l’autorise, y dessine. Un cinquième mode, *Maquette*, sert à prototyper des écrans comme dans Whimsical : fenêtre de navigateur, téléphone, barre de navigation, onglets, boutons, champs, cases, interrupteurs, cartes, fenêtres de dialogue…, chacun avec ses réglages. Les outils Forme et Composant de maquette ouvrent une palette en colonne où chaque élément se voit tel qu’il sera posé, avec une recherche. Les liens se règlent finement : épaisseur (jusqu’à la grosse flèche pleine), accroche précise le long d’un côté, points de passage, segments à décaler, sauts aux croisements et animations (tirets, points, pulsation, comète). Un tableau ou une sélection s’exporte en PNG, WebP, SVG ou PDF, avec un aperçu, dans le thème par défaut (le même pour tous) ou dans celui qu’on choisit ; un diagramme draw.io s’importe (fichier `.drawio` ou XML, images intégrées comprises). Le bouton *Historique*, à côté d’Annuler, parcourt les versions du tableau, entoure ce qui a changé, et permet de restaurer une version ou de la copier dans un nouveau tableau ; une version étiquetée (« v2 »…) n'est jamais effacée, garde ses images et ses icônes ajoutées même supprimées ensuite, et se cite avec `@` (`@[Architecture · v2](board:7#v:49)`) : le lien ouvre le tableau sur elle, et son aperçu la dessine. Comme dans Whimsical, ce qu’on déplace ou redimensionne s’aimante sur les éléments voisins : bords et centres alignés, ou écart égal entre voisins, montrés par des traits de guidage et l’écart, sinon la grille ; l’aimant de la barre d’outils l’active ou le coupe (choix retenu sur l’appareil), et Alt s’en passe le temps d’un geste. Un clic sur l’avatar d’une personne présente la suit, comme dans Figma : la vue cadre ce qu’elle regarde (déplacements, zoom, changement de tableau) jusqu’à la première action.

**Déplacer vers un autre espace** — dans l’arbre de la documentation ou des tableaux blancs, clic droit sur un ou plusieurs éléments (Ctrl + clic, Maj + clic), « Déplacer vers… » : on choisit l’espace d’arrivée (où l’on est éditeur) et, au besoin, un de ses dossiers. Un dossier part avec son contenu ; un nom déjà pris devient « Nom (2) ». Chaque élément garde son identifiant, donc son historique, ses commentaires, ses étiquettes de version et son lien de partage ; les images d’un tableau sont copiées dans le nouvel espace. Il quitte aussitôt l’ancien espace pour qui n’a pas accès au nouveau, assistant IA et recherche sémantique compris.

**Étiquettes d’espace** — clic droit sur un espace de documentation, un espace de tableaux blancs ou un projet, « Étiquettes de l’espace… » (« Étiquettes du projet… ») : on pose une étiquette (« v1.0 », « Livré au client »), qui fige tout le contenu tel qu’il est, fichiers compris (arbre, notes, modèles et images ; tableaux, modèles, images et icônes ajoutées ; export complet du projet, tickets, commentaires, historique et pièces jointes). Ces copies sont rangées à part, par empreinte (un fichier inchangé d’une étiquette à l’autre n’est gardé qu’une fois, dans `uploads/frozen`, inclus dans les sauvegardes) : modifications, corbeille vidée, historique purgé, images remplacées ou supprimées ne changent plus l’étiquette. Chacune se *consulte* en lecture seule (page `/etiquettes/<id>` : arbre et notes rendues, tableaux dans l’éditeur sans écriture, tickets par colonne avec leur détail), se *télécharge* en ZIP et, pour la documentation et les tableaux blancs, redonne un *nouvel espace* au contenu d’alors. Les éditeurs (« Configurer le projet » pour un projet) en posent ; le propriétaire de l’espace, ou qui l’a posée, la supprime. Supprimer l’espace emporte ses étiquettes.

**Mentions et recherche** — taper `@` propose personnes, tickets, notes, tableaux blancs et versions étiquetées, avec des pastilles pour filtrer par type (chacun son icône et sa couleur) et « Voir tout… » quand la liste ne suffit pas. La recherche Ctrl + K a les mêmes pastilles (Tab passe de l’une à l’autre) et trouve aussi les tableaux blancs. Dans une note, « Image » réutilise une image de l’espace (recherche, vignettes) ou en importe une ; chaque bloc de code affiche son langage dans une pastille, qu’un clic change. L’adresse d’une note suit l’endroit lu (`#etape-2+12` : le titre au-dessus et le décalage en lignes, `#L57` sans titre au-dessus) : on y revient en changeant de note ou avec Précédent, et un lien partagé mène au même endroit.

**Authentification LDAP** — dans *Administration → Authentification* (permission `auth.manage`), activez la connexion par annuaire : serveur, chiffrement (LDAPS, StartTLS ou aucun), compte de service, base et filtre de recherche, attributs de l'adresse et du nom, rôle des nouveaux comptes. Deux profils préremplissent ces champs, qui restent modifiables : **classique** (nom lu tel quel) et **spécifique** (compte de service obligatoire, recherche par adresse e-mail, nom écrit « NOM, Prénom (Société) » repris en « Prénom NOM »). Un bouton teste les réglages étape par étape sans rien enregistrer. À la connexion, un compte local garde son mot de passe ; sinon l'annuaire vérifie celui de la personne, et son compte est créé à la première connexion. Les mots de passe des personnes ne sont jamais enregistrés ; celui du compte de service l'est chiffré.

**Supervision (administration)** — deux pages réservées aux permissions `monitoring.view` et `logs.view` :
- **Performances** — santé globale, trafic, erreurs, latences (médiane, p95, p99, répartition), routes de l'API les plus lentes, processeur, mémoire, retard de la boucle d'évènements, connexions WebSocket, requêtes SQLite, taille de la base et des pièces jointes. Fenêtres de 15 min à 3 jours, rafraîchissement automatique ; les indicateurs sont agrégés par minute et survivent aux redémarrages (3 jours conservés).
- **Journaux** — erreurs serveur (avec pile d'appels), accès refusés, requêtes lentes, connexions et échecs de connexion, actions d'administration, jetons d'API, pièces jointes. Filtres (niveau, source, texte, période, requête), suivi en direct, export NDJSON. Chaque réponse porte un `X-Request-Id` pour retrouver l'erreur vue par un utilisateur. Conservation 14 jours.

**Description en Markdown** — barre d'outils (gras, titres, listes, tâches, liens, tableaux, code), formules mathématiques (KaTeX), diagrammes Mermaid, mentions `@`, et mode plein écran (éditeur et aperçu côte à côte). Le rendu est assaini (DOMPurify) ; Mermaid est chargé à la demande.

**Assistant IA** — bouton « cerveau » en bas de la barre latérale : un panneau latéral (façon Gemini dans Workspace) qui connaît le projet et le ticket ouverts, cherche sur tous les champs dans un projet ou partout, lit avec les droits de la personne et, si elle coche « Autoriser les modifications » et en a le droit, crée, modifie, déplace et commente des tickets (« via Assistant IA » dans l'historique). On peut joindre des fichiers à une question (trombone, glisser-déposer ou coller) : PDF, CSV et autres fichiers texte, dont le texte est extrait dans le navigateur (PDF.js) et lu par tous les modèles, ainsi que des images et des PDF scannés pour les modèles avec vision. Le bouton « Éditer » du contexte lui donne d'autres projets, tickets, espaces ou notes, avec des suggestions (éléments parents et en lien). Sur la documentation, il connaît la note ouverte, cherche et lit dans les espaces accessibles et, avec les mêmes garde-fous et le rôle de la personne, crée (au besoin d'après un modèle de l'espace) ou retouche des notes ; chaque changement s'affiche ligne à ligne et s'annule. Il liste les images d'une note, d'un espace, d'un tableau blanc ou d'un ticket et, avec un modèle qui a la vision, les regarde ; sur un tableau blanc ouvert, il le voit d'emblée dessiné et peut en regarder de près une zone ou des éléments (le serveur ne dessine pas : c'est le panneau qui dessine ces vues à sa demande, pendant la réponse). Les images regardées s'affichent dans ses étapes. Il cite ce dont il parle par des liens qui ouvrent l'élément (tickets, projets, notes, tableaux blancs) et liste sous sa réponse les sources qu'il a lues ; une citation de lignes d'une note (`@[Guide](doc:12#L4-9)`, plusieurs passages : `#L3-5,9`) ouvre la note sur ces lignes surlignées, en lecture comme en écriture, et une citation d'éléments d'un tableau (`@[Schéma](board:7#el:a1b2c3,d4e5f6)`) ouvre le tableau sur eux, sélectionnés. Ces liens s'écrivent aussi à la main dans une note, un ticket ou un commentaire. **Recherche sémantique (RAG)** : dans *Administration → IA*, un modèle d'embeddings compatible OpenAI (`POST /v1/embeddings` : Ollama, LM Studio, vLLM, OpenAI…) indexe les tickets, notes et tableaux des projets et espaces qui l'activent dans leurs réglages (désactivé par défaut : *Réglages → Général* d'un projet, *Modifier l'espace* d'un espace de documentation ou de tableaux). Le format des requêtes s'adapte au modèle (EmbeddingGemma et EmbeddingGemma 2 : `task: search result | query:` / `title: … | text:` ; Nomic Embed : `search_query:` / `search_document:` ; Qwen3 Embedding : consigne `Instruct: … Query:` pour la question), ou se règle à la main ; le bouton *Tester* vérifie que le modèle répond et qu'une question est bien plus proche du passage qui y répond. L'index se met à jour tout seul toutes les X heures ou jours (seul ce qui a changé est recalculé), et se reconstruit si le modèle change. L'assistant reçoit alors l'outil `search_knowledge`, qui ne fouille que les projets où la personne peut interroger l'IA et les espaces dont elle est membre ; les passages trouvés se citent (lignes d'une note, éléments d'un tableau). Fournisseur compatible OpenAI v1 (OpenAI, Mistral, Ollama, LM Studio…) configuré dans *Administration → IA* (en HTTPS, les autorités de confiance du système sont reconnues, et « Vérifier le certificat HTTPS » se désactive pour un serveur au certificat auto-signé) ; permissions globales (`ai.use`, `ai.manage`) et par projet (`ai.read`, `ai.write`). Dans *Administration → IA*, chaque modèle a ses réglages de réflexion, ceux que le panneau propose : préréglages OpenAI, Qwen et DeepSeek V4.1 Flash, ou une liste personnalisée (nom et paramètres envoyés au fournisseur).

**Correcteur orthographique** — celui du navigateur souligne les fautes dans les notes, les tickets, les commentaires et les tableaux blancs, dans les langues choisies dans ses réglages (plusieurs à la fois si besoin) ; FastBoard ne reçoit rien. Chacun le coupe dans *Mon compte → Préférences* (choix enregistré sur le compte). Les zones de code (JSON, XML, Mermaid, recherche) ne sont jamais vérifiées.

**Accueil** — premier onglet de la barre latérale, et page d’arrivée après la connexion (`/accueil`) : les espaces favoris en tête (documentation, tableaux blancs, projets), puis ce qui vous est assigné (tickets ouverts dont votre part n’est pas finie, par échéance, retards en rouge), vos notifications importantes (mentions et assignations non lues), ce que vous avez modifié récemment (notes, tableaux et tickets, que vous ayez écrit en dernier ou contribué à leur historique) et vos documents favoris. Il se met à jour tout seul à l’arrivée d’une notification. Un espace ou un projet se met en favori d’un clic sur l’étoile de sa carte (ou de son clic droit) ; ses favoris passent en tête des listes.

**Découper en sous-tickets** — dans l’avancement d’un ticket, le menu « ⋯ » à droite du « + » propose « Découper en sous-tickets… » : une fenêtre montre ce que deviendra chaque ligne (titre, personne, statut), puis chaque ligne devient un sous-ticket qui reprend sa personne et son avancement (terminée → « Terminé », commencée → « En cours »), ainsi que la catégorie, la priorité, la livraison, les composants et les dates du ticket, pour la suivre à part. Le ticket suit ensuite l’avancement de ses sous-tickets.

**Images dans la description d’un ticket** — une image collée (capture, Ctrl V) ou glissée dans la description est jointe au ticket et s’affiche à l’endroit du curseur, en Markdown (`![nom](/api/attachments/12/download?inline=1)`) ; un autre fichier devient un lien de téléchargement. Le bouton « Image » de la barre d’outils choisit une image déjà jointe au ticket (vignettes, recherche) ou en importe une ; une image lâchée sur la description affichée l’ouvre en édition et s’ajoute à la fin. Remplacer la pièce jointe (clic droit) change l’image partout où elle est citée ; un clic sur l’image l’agrandit.

**Notifications** — cloche en bas de la barre latérale : changements des tickets suivis (bouton « Suivre » ; créateur, assignés, commentateurs et personnes mentionnées suivent automatiquement, sauf quand l'action vient d'un jeton d'API : un agent qui crée ou commente des tickets avec votre jeton ne vous y abonne pas), assignations et mentions `@`, en direct. Chacun choisit son niveau projet par projet (cloche en haut du projet, ou *Mon compte → Notifications*) : « Tout » (toute l'activité des tickets), « Ma participation » (par défaut : tickets suivis, assignations, mentions), « Mentions et assignations » ou « Aucune ». Sur demande, et pour ce navigateur seulement, une notification système s'affiche quand l'application n'est pas au premier plan (HTTPS ou localhost requis) ; un clic ouvre le ticket ou la note. Les notifications se trient par catégorie (mentions, assignations, commentaires, changements, chacune avec ses non lues) ; « Voir toutes les notifications » ouvre leur page (`/notifications`, regroupées par jour), et le menu « ⋯ » marque tout comme lu, efface les notifications lues ou toutes (dans la catégorie choisie) ; la croix d’une notification l’efface seule.

**Clic droit sur un ticket** — renommer, assignés, dates, priorité, livraison, colonne, ou déplacement vers un autre projet (nouvelle clé, listes reprises par leur nom). **Clic droit sur un projet** (page d'accueil) — export CSV ou JSON complet.

**Recherche globale** — en haut à droite (`Ctrl+K`) : projets, tickets et utilisateurs, aperçu instantané et page « tous les résultats ». **Page utilisateur** : projets communs, tickets en cours, actions des 30 derniers jours.

**Personnalisation et maintenance (administration)** — nom et logo de l'application (en-tête, page de connexion, onglet du navigateur) ; bandeau de maintenance à trois niveaux (information, perturbations, interruption), programmable, diffusé en direct à tous.

**Sauvegardes (administration)** — activables, vers un ou plusieurs dossiers : archive ZIP de la base, des pièces jointes et de la clé de chiffrement, **incrémentale** (seules les nouvelles pièces jointes, chaîne de N archives), planification quotidienne ou toutes les N heures, conservation façon Duplicati (tout garder, N dernières, durée, *intelligente* 1W:1D,4W:1W,12M:1M ou règles personnalisées), historique et sauvegarde immédiate. Chaque archive contient un `README.txt` de restauration.

**Version et nouveautés** — la version s'affiche sous le nom de l'application ; un clic ouvre le journal des modifications ([`shared/changelog.ts`](shared/changelog.ts), voir [AGENTS.md](AGENTS.md)).

**Annuler / rétablir** (`Ctrl+Z`, `Ctrl+Maj+Z` / `Ctrl+Y`) pour les déplacements, changements de dates, statuts, etc. Raccourci `N` : nouveau ticket.

**Comptes et permissions**
- Seul un administrateur crée les comptes (ou l'annuaire LDAP, s'il est activé). Chaque utilisateur modifie son **nom**, son **image de profil** (recadrée automatiquement), son mot de passe et son **thème**.
- **14 thèmes** répartis en *clairs* et *sombres* (presets Aura, Lara, Nora, Material), enregistrés sur le compte et appliqués instantanément.
- **Thèmes personnalisés** (*Mon compte → Apparence*) : en plus de la couleur principale et des surfaces, chaque couleur se règle une à une, celles de l’interface (fonds, panneaux, bordures, textes) comme celles du rendu Markdown (titres 1 à 6, gras, italique, liens, code, blocs de code, citations, surlignage, tableaux, lignes, puces, étiquettes), avec un aperçu en direct, et le thème peut avoir ses propres polices. Un thème s’exporte en fichier `.fastboard-theme.json` (à envoyer, puis à importer), ou se publie dans la bibliothèque du site, où chacun l’ajoute à ses thèmes d’un clic.
- **Lecture des notes** : le texte se centre sur l’écran (même avec l’arbre et le sommaire ouverts), dans sa colonne, ou prend toute la largeur sans marges ; la police et la taille du texte des notes se choisissent à part.
- **Connexion** : la session dure tant qu’on s’en sert (elle n’expire qu’après 30 jours sans utilisation), et la page de connexion peut mémoriser l’adresse e-mail sur le navigateur.
- **Rôles globaux** (super admin, administrateur, membre, invité…) et **rôles de projet** (propriétaire, gestionnaire, éditeur, contributeur, lecteur…), tous personnalisables dans *Administration → Rôles et permissions* (matrice de permissions). On ne peut jamais accorder plus de droits que les siens, ni modifier un compte plus privilégié que le sien, ni retirer le dernier super administrateur / propriétaire.
- Partage de projet : le propriétaire invite des utilisateurs existants avec le rôle de son choix.
- **Groupes** (onglet *Groupes*) : on rassemble des personnes dans un groupe, puis on l’ajoute d’un coup à un projet, un espace de documentation ou de tableaux blancs, avec un rôle (par exemple Lecteur). Une personne du groupe peut recevoir en plus son propre rôle (par exemple Éditeur) : comme sur Google Drive, le rôle le plus large l’emporte. Ajouter ou retirer quelqu’un du groupe change ses accès aussitôt, y compris pour l’assistant IA et la recherche sémantique. Le créateur gère le groupe et peut nommer d’autres gestionnaires ; un groupe n’est jamais propriétaire.

**API pour les IA et les scripts** — tout ce que fait l'interface est disponible en REST. Un utilisateur crée des **jetons d'API** (menu du compte → *Jetons d'API*) : portée lecture seule ou lecture/écriture, projets accessibles, expiration (prolongeable), **nom d'affichage** (« via … » dans l'activité et l'historique), révocation immédiate ; le secret `fb_…` est stocké chiffré (clé `data/secret.key`) et peut être **réaffiché** par son propriétaire après saisie de son mot de passe. Un jeton agit avec les droits de son propriétaire, jamais davantage, avec une limite de débit, et ne peut ni administrer ni gérer d'autres jetons. Documentation :
- **Swagger UI** : `/api/docs` · **OpenAPI 3.1** : `/api/openapi.json` (générée depuis les schémas de validation réels, un test garantit qu'elle décrit chaque route) ;
- **Guide pour les IA** (concepts, recettes `curl`, bonnes pratiques, exemple de consigne) : [`docs/API.md`](docs/API.md), aussi servi sur `/api/docs/guide.md`.

```bash
curl -s http://localhost:3000/api/projects/1/tickets?status=in_progress -H "Authorization: Bearer fb_…"
```

### Temps réel

Les modifications passent par l'API REST (validation et permissions côté serveur) ; le serveur diffuse ensuite un évènement à tous les clients abonnés au projet via `/ws` (`ticket.updated`, `comment.created`, `members.changed`…). Le client applique chaque évènement de façon idempotente (comparaison de `updatedAt`) et met à jour son interface instantanément (mise à jour optimiste pour les déplacements et les dates). Après une coupure, le projet est rechargé à la reconnexion. Le protocole est décrit dans [`shared/realtime.ts`](shared/realtime.ts).

### Modèle de permissions

Une permission est une chaîne (`ticket.edit`, `project.members`, `tokens.create`…) ; le catalogue est dans [`shared/permissions.ts`](shared/permissions.ts). Les droits d'un utilisateur dans un projet = l'union de ceux de son rôle de projet direct et des rôles des groupes dont il fait partie (`projects.manage_all` donne tous les droits partout, `projects.view_all` donne la lecture seule). Les vues SQL `project_access`, `doc_access` et `board_access` réunissent membres directs et accès par groupe : toutes les vérifications (API, jetons, WebSocket, assistant IA, recherche sémantique) passent par elles. Les rôles sont des lignes en base : créez les vôtres sans toucher au code.

## Configuration

Variables d'environnement (toutes facultatives) :

| Variable | Défaut | Rôle |
| --- | --- | --- |
| `PORT` / `HOST` | `3000` / `0.0.0.0` | Adresse d'écoute |
| `FASTBOARD_DB` | `data/fastboard.sqlite` | Fichier de base de données |
| `NODE_ENV` | — | `production` active l'en-tête CSP |
| `FASTBOARD_UPLOADS` | `<dossier de la base>/uploads` | Dossier des pièces jointes |
| `FASTBOARD_MAX_UPLOAD_MB` | `25` | Taille maximale d'une pièce jointe |
| `FASTBOARD_LOG_LEVEL` | `info` | Niveau minimal des journaux conservés (`debug` journalise chaque requête) |
| `FASTBOARD_LOG_CONSOLE` | `1` | `0` : ne pas recopier les journaux sur la console |
| `ALLOWED_ORIGINS` | — | Origines supplémentaires acceptées derrière un proxy (séparées par des virgules) |
| `FASTBOARD_HTTPS` | — | `0` : ignorer les réglages HTTPS au démarrage (secours si un certificat bloque l'accès) |

**HTTPS** : *Administration → HTTP / HTTPS* sert le site en HTTPS sur un second port avec vos certificats (PEM ou PFX, ou un certificat auto-signé pour essayer), avec redirection HTTP → HTTPS et HSTS en option ; c'est appliqué sans redémarrer et les certificats renouvelés sont relus automatiquement. Depuis la machine elle-même, HTTP n'est jamais redirigé (accès de secours).

Derrière un reverse proxy HTTPS, transmettez les en-têtes `Upgrade`/`Connection` pour `/ws` et `X-Forwarded-Proto` ; le cookie de session devient alors `Secure`. Cochez « Derrière un proxy inverse » dans *HTTP / HTTPS* pour que FastBoard fasse confiance aux en-têtes `X-Forwarded-*`.
